# BZaudio Roadmap

This roadmap is staged deliberately. Each stage must be usable and tested before it becomes a dependency for the next.

## Stage 0 — Trusted foundation
**Status: In progress**

- Establish the BZaudio brand, public website, and clear equipment categories.
- Preserve the working SoundMatch guided planning flow.
- Preserve installation and consultation information.
- Keep browser-based audio tools useful, explainable, and honest about their limits.
- Establish the PROJECT: ORIGIN public project hub.
- Keep quote requests as a transparent inquiry/brief workflow; no checkout or payment is implied.

**Exit criteria:** core website routes work, existing tools remain functional, accessibility and responsive checks pass, and supplier claims remain verified.

## Stage 1 — Browser audio workspace
**Status: Planned / incremental**

- Improve the browser-based toolbox and audio calculators.
- Make system planning, signal-flow guidance, and reusable workflows easier to navigate.
- Build clear equipment and console-specific knowledge structures.
- Introduce model-specific compatibility test fixtures before any live control or transfer claim.
- Keep local-only features clearly distinguished from account-backed or connected features.

**Exit criteria:** each tool has defined inputs, units, assumptions, validation, tests, and a clear statement of what it does not calculate or control.

## Stage 2 — Desktop platform (Windows + macOS)
**Status: Vision / research**

- Establish the shared BZaudio application architecture and workflow model.
- Bring browser capabilities into a dedicated desktop workspace where that materially improves reliability and show use.
- Design a console compatibility layer with explicit adapters for each supported model.
- Prioritize Allen & Heath; verify each model and firmware combination individually.
- Research safe, documented show-file and workflow exchange with other manufacturers, including Yamaha, without promising lossless cross-vendor conversion.

**Exit criteria:** at least one named console model has a reproducible, tested integration with documented limitations; no family-wide claims based on a single model.

## Stage 3 — Touchscreen audio controller
**Status: Vision / research**

- Define the controller's physical workflow, display hierarchy, connectivity, and fail-safe behavior.
- Prototype high-value show controls and navigation before committing to hardware.
- Validate the controller against the desktop platform and specific supported console integrations.
- Make connection state, control ownership, and failure recovery visible to the operator.

**Exit criteria:** prototype usability testing and end-to-end integration tests demonstrate predictable operation and safe fallback behavior.

## Stage 4 — Dedicated-device operating system
**Status: Vision / research**

- Build the focused device OS around the proven desktop and controller workflows.
- Unify device setup, profiles, tools, and supported integrations.
- Establish update, recovery, permissions, and offline behavior before public release.
- Expand supported equipment only through documented, model-specific verification.

**Exit criteria:** stable device lifecycle, recovery strategy, compatibility matrix, and sustained real-world testing.

## Ongoing quality gates
- No universal compatibility claims without evidence.
- No invented product or supplier data.
- No false precision in acoustic, SPL, coverage, or electrical calculations.
- Accessibility, keyboard support, responsive layouts, and reduced-motion support.
- Automated tests and production builds at each meaningful milestone.
- Separate approval before production deployment, payments, customer accounts, external services, or domain/DNS changes.
